# フェーズ0 検証報告（要件定義書 7.1）

2026年10月20日 · 対象: LibreBooking 3.5.1（公式Dockerイメージ `librebooking/librebooking:7.1.0-3.5.1`）＋ MariaDB 11.4

## 結論

11項目のうち、LibreBookingの標準・設定だけで要件を満たせたのは **V-06・V-11の2項目**。残りは「拡張サービスで補う」か、一部「不可」だった。加えて、拡張サービスから使う予定だった**APIに不具合が2件**ある（ユーザー作成、グループ権限の更新。開発版 `develop` でも未修正）。

7.1の判定基準（「不可」や「拡張サービスで補う」が多い場合は作成者が判断）に当たるため、ここで止めて判断を仰ぐ。判断材料は末尾の「判断のための整理」に書いた。

## 判定一覧

| No. | 確かめること | 判定 | 根拠 |
| --- | --- | --- | --- |
| V-01 | 講師ごとの空き時間（曜日の時間帯、日付の例外）。講師本人が設定できるか | 拡張サービスで補う | 講師ごとにスケジュールを分ければ、曜日ごとの時間帯（レイアウト）と日付の例外（休止枠）は管理画面で設定できる。ただし**スケジュール・レイアウト・休止枠を書き換えるAPIがない**（`POST /Schedules/` は405）。講師はLibreBookingの画面を使わない方針（4.4）なので、講師本人の設定は拡張サービスで持つしかない |
| V-02 | 生徒ごとに担当講師だけ予約可能にし、担当外をAPIで拒否 | 設定で可（APIに不具合） | 講師ごとに「担当:講師A」のようなグループを作り、そのグループにだけ講師Aの予約権限を付ける。生徒をグループに入れると、生徒の `/Resources` は担当講師だけを返し、担当外は「リソースを使用する権限がありません」で拒否された。グループへの生徒の追加はAPIでできる。**グループに権限を付けるAPIは「更新しました」と返すが保存されない**（後述の不具合）ため、講師を追加したときに管理画面で1回設定する |
| V-03 | 講師ごとの担当レッスン一覧と空き時間の更新をAPIで | 一覧は標準で可／更新は不可 | `GET /Reservations/?resourceId=` で講師ごとの予約が取れる。空き時間の更新はV-01のとおりAPIがない |
| V-04 | 予約・変更・キャンセルごとの締切。管理者は締切・公開期間を無視できるか | 標準で可（RS-05とは差あり） | リソースごとに `minNoticeAdd / minNoticeUpdate / minNoticeDelete / maxNotice` があり、生徒は締切後・公開期間外を拒否され、管理者は代理予約できた。ただしLibreBookingは**締切後のキャンセル自体を拒否する**。要件（RS-05）は「締切後もキャンセルできるが回数は戻らない」なので、この部分は拡張サービスで補う |
| V-05 | クレジットの消費と返却。月ごとの回数を表せるか | 拡張サービスで補う | 予約で1減り、締切前キャンセルで1戻ることは確認できた。しかし①残高は**1人1つ**で、月ごとの回数を持てない ②削除すると**締切後でも常に返却**される（RS-05に反する）③管理者の予約は残高チェックを飛ばし、**残高がマイナス**（-6）になった ④残高を読み書きするAPIがない（検証ではDBを直接更新した）。回数は拡張サービスで管理し、LibreBookingのクレジット機能は使わない |
| V-06 | 管理者の繰り返し予約 | 標準で可 | APIで毎週の繰り返し予約（8回分）を作れた。RS-07の「回数が足りない月の警告」は標準にないため、拡張サービスで出す |
| V-07 | 保護者1人に複数の子ども | 不可 → 拡張サービスで補う | 保護者と子どもを結ぶ仕組み（表）がない。他人の代わりに予約できるのは管理者だけ。子どもごとにLibreBookingの利用者を作り、保護者との紐付けは拡張サービスで持つ |
| V-08 | 自己登録のON/OFF、承認待ち | ON/OFFは設定で可／承認待ちは拡張サービスで補う | `registration.allow.self.registration` でON/OFFできる。ただし状態は「有効・メール認証待ち・無効」だけで、**管理者の承認待ち**はない（自己登録した利用者はすぐ予約できる状態になった） |
| V-09 | 外部から予約・ユーザー・権限を操作するAPI | 一部不具合 | 予約の作成・更新・削除・承認・一覧はそろっている。ただし次の制約・不具合がある（下表） |
| V-10 | 日本語の品質、スマホでの管理画面 | 設定で可（課題あり） | 日本語訳は大部分そろっているが、「Owner」「Showing page 1 of 1」「Display … records per page」など英語が残る。日付は `2026-10-19` 形式で、UI-18（「10月20日（火）」）とは違う。スマホでは表が詰まって読みにくい（`docs/phase0/*.png`）。管理者が毎日使う画面としては、予約カレンダー以外は新しく作るほうがよい |
| V-11 | 公式Dockerイメージのバージョン固定と更新 | 標準で可 | タグは `<イメージ版>-<LibreBooking版>`（例 `7.1.0-3.5.1`）で固定できる。更新はタグを変えて起動し直し、`/install/configure.php` でDBを更新する。検証環境で試してからタグを本番に反映する（7.2） |

### V-09 の詳細

| 操作 | 結果 |
| --- | --- |
| 予約の作成・更新・削除・承認・一覧 | 可。ただし作成時は省略できるはずの項目（`description`、`participants` など）もすべて送らないとサーバーエラーになる |
| ユーザーの作成 `POST /Users/` | **不具合**: 管理者で呼んでも「Only application administrators may create users」で拒否される |
| グループの権限 `POST /Groups/{id}/Permissions` | **不具合**: 「更新しました」と返るが保存されない |
| グループの利用者 `POST /Groups/{id}/Users` | 可 |
| 自己登録 `POST /Accounts/` | 可（`api.registration.allow.self` をONにした場合。ONにすると誰でも有効な利用者を作れるため、本番では外から届かない場所に置く必要がある） |
| クレジットの読み書き | APIなし |
| スケジュール・レイアウト・休止枠の書き込み | APIなし |

**不具合の原因**: API呼び出しのログイン情報が、管理画面と共用している内部処理（`ManageUsersService::AddUser`、`ManageGroupsPresenter::ChangePermissions`）に渡っていない。内部処理はWebのログイン状態（`ServiceLocator::GetServer()->GetUserSession()`）を見るため、APIからは未ログイン扱いになる。開発版（`develop`タグ、2026年10月19日）でも同じコードだった。本体を改造しない方針（2章の2）なので、こちらでは直せない。上流に報告する価値はある。

## 判断のための整理

LibreBookingを使い続ける場合、役割はおおむね次のように分かれる。

| LibreBookingに任せられる | 拡張サービスで作る必要がある |
| --- | --- |
| 予約の保存と重複の防止 | 講師の空き時間（講師画面から更新するため） |
| 予約・変更・キャンセルの締切、公開期間 | 締切後キャンセル（取り消すが回数は戻さない） |
| 担当講師による予約権限（グループ） | 月ごとの回数、繰越・失効、回数不足の警告 |
| 管理者の予約カレンダー、代理予約、繰り返し予約 | 保護者と子ども、承認待ち、招待コード |
| | 体験枠、休講時の一括取消と回数返却、講師都合キャンセルの集計 |
| | 生徒・講師の画面、決済、通知、ダッシュボード、生徒詳細など |

気になる点:

1. **ルールが2か所に分かれる**: 回数と空き時間は拡張サービス、締切と権限はLibreBookingに置くことになり、「ルールは1か所に置く」（2章の6）を守りにくい。生徒の予約は必ず拡張サービスを通し、拡張サービスが空き時間・回数を確かめてからLibreBookingに書き込む形になる。
2. **空き時間が二重になる**: 講師が拡張サービスで設定した空き時間を、LibreBookingのスケジュールへ反映するAPIがない。LibreBookingの管理カレンダー上では空き時間が分からず、松田さんが空いていない時間に代理予約できてしまう。
3. **API不具合の回避策が必要**: 生徒の登録（ST-01）を拡張サービスから自動で行うには、自己登録APIを使うかDBを直接書くことになる。
4. **管理画面の多くを新しく作る**: 4.1ですでに生徒・料金・ダッシュボードなどは新規。LibreBookingの標準画面で残るのは予約カレンダー・代理予約・繰り返し予約・各種設定だが、そのうち設定（締切、公開期間）は回数ルールと一緒に拡張サービス側にあるほうが分かりやすい。

**作成者への提案（判断は作成者が行う）**: 予約の中核も拡張サービス（TypeScript）で自前で作り、LibreBookingは使わない案を勧める。理由は、回数・空き時間・締切・権限を1か所（2章の6）で判定でき、APIの不具合を避けられ、サーバーもPHP＋MariaDBを持たずに済むから。代わりに、管理者の予約カレンダー・代理予約・繰り返し予約の画面を新しく作る分の作業が増える。

LibreBookingを使い続ける場合は、上の「拡張サービスで作る必要がある」列をすべて作り、V-02の権限は講師追加時に管理画面で設定する運用になる。

## 再現方法

```sh
cp .env.example .env   # 値を埋める。LB_LOAD_SAMPLE_DATA=true, LB_API_REGISTRATION_ALLOW_SELF=true
docker compose -f infra/librebooking/compose.yml --env-file .env up -d
bash phase0/verify.sh  # 実行結果の例: docs/phase0/verify-output.txt
```

検証はダミーデータだけで行った。時間枠（日本時間 10:00〜21:00、60分）と、APIで設定できない項目（クレジット残高、グループの権限）は、管理画面の操作に相当するDB更新で代用した（スクリプト内に明記）。
