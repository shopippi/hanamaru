## 1. 概要

音楽教室の在籍生徒だけが使えるレッスン予約と、回数券（月額サブスクリプション）の管理システムを作る。生徒と保護者はスマホで予約と支払いを行い、松田さんはスマホの管理画面だけで日々の運用を回す。

### 1.1 ロール

| ロール | 担当 | できること |
| --- | --- | --- |
| 生徒（保護者を含む） | 在籍生徒 | 担当講師の枠の予約・キャンセル、残り回数の確認、支払い、担当講師のプロフィール閲覧 |
| 講師 | 採用した講師 | 自分の担当レッスンの確認、自分の空き時間の設定 |
| 管理者 | 松田さん | すべての設定、生徒・講師の管理、全予約の操作、入金記録、解約・休会 |
| 開発・保守 | 作成者（Claude Codeを使用） | 開発、OSSの更新、障害対応、本番への反映 |

### 1.2 リリース範囲

| 区分 | 時期 | 範囲 |
| --- | --- | --- |
| フェーズ0（検証） | 完了（2026年10月20日） | LibreBookingで要件が実現できるかの検証（7.1）。結果により予約の中核も自前で作ることに決定 |
| 初回リリース | 公開条件（8.1）をすべて満たした時点で、できるだけ早く公開する。遅くとも2026年12月 | 3章の要件すべて（体験レッスンの申込、コンビニ払い・PayPay、単発の請求、招待コードを含む） |
| 将来 | 規模拡大時 | LINE連携、公式HP（別途作成してマージ）、講師プロフィールのCMS化 |

公開の時期は実装の都合で分けず、テストで要件どおりに動くことを確かめられた時点で、すべての機能をそろえて公開する。

対象外: 発表会の申込など、予約・請求以外の申込機能。

## 2. 設計方針

運用ルールはコードに固定せず、松田さんが管理画面から変えられる設定値にする。一度設定すれば日常的に触らなくても回る状態をゴールにする。

1. **設定で変えられるようにする**: 締切、回数、料金、公開期間などの値はすべて設定項目にする（3.8）。コードに数値を直接書かない
2. **予約の中核も自前で作る**（v1.8で変更）: 当初はOSSのLibreBookingを土台にする予定だったが、フェーズ0の検証で、月ごとの回数・講師による空き時間の更新・保護者と子ども・承認待ちを表現できず、APIにも不具合があったため、予約・空き時間・締切・回数・権限をすべてTypeScriptのサービス（API）で作る。決めた経緯は `docs/decisions/0001-build-booking-core.md` と `docs/phase0-report.md`
3. **画面はすべて新しく作る**: 生徒（スマホ前提・ホーム画面アプリ）、講師、管理者の3つの画面をTypeScriptで作り、どれもAPIだけを呼ぶ
4. **画面と処理を分ける**: 予約・確認・キャンセル・残り回数・支払いの処理はAPIとして作る。将来LINE内の画面を足すときは同じAPIを呼ぶだけにする
5. **通知の送り先を差し替えられるようにする**: 今はメールだけを実装する。生徒データにはLINEの識別子を後から入れられる欄を用意する
6. **ルールは1か所に置く**: 予約の締切や回数のルールは1か所でだけ判定し、画面ごとに重複して持たない
7. **カード情報を扱わない**: 決済はStripeの決済画面とカード管理画面に任せ、カード情報がこちらのサーバーを通らないようにする

### 3.4 空き時間と予約

回数の数え方: 回数は「レッスン日が属する月」の回数から使う。生徒は、その月の残り回数の範囲で予約できる。翌月分は、自動課金が有効な生徒に限り、月額コースの回数を上限に先に予約できる。翌月1日の課金が失敗し、猶予期間を過ぎた場合は、翌月分の予約を取り消す。

| ID | 内容 | 受入条件 | 段階 |
| --- | --- | --- | --- |
| AV-01 | 講師本人と管理者が、講師の空き時間（曜日ごとの時間帯、日付ごとの例外）を設定する | 講師が設定した枠が、担当生徒の予約画面に表示される | 1 |
| AV-02 | 予約が入っている時間帯を変更・削除しようとすると、件数・生徒名・日時を並べた強い警告を出す | 警告で確認しなければ変更されない | 1 |
| AV-03 | 警告を承知で変更した場合、影響する予約を「講師都合のキャンセル」として取り消す | 予約が取り消され、回数が生徒に戻り、生徒と管理者にメールが届く | 1 |
| AV-04 | 管理者が休講日・臨時休講を設定する。既存の予約は「教室都合のキャンセル」として扱う | 休講日の枠は表示されず、既存の予約は取り消されて回数が戻る | 1 |
| AV-05 | 講師都合のキャンセル件数を、講師ごとに管理者が確認できる | 管理画面に講師別の件数が表示される | 1 |
| RS-01 | 生徒は担当講師の空き枠から予約する。予約すると回数を1つ使う | 予約するとその月の残り回数が1減る | 1 |
| RS-02 | 残り回数が0、未払いで猶予期間を過ぎた、または休会中の生徒は予約できない | 予約ボタンが押せず、理由（例:「今月の回数を使い切りました」）が表示される | 1 |
| RS-03 | 生徒に予約を公開する期間（何週間先まで）を設定する | 期間より先の日付は生徒に表示されない | 1 |
| RS-04 | 締切より前のキャンセル・変更では回数を戻す。締切は予約・変更・キャンセルごとに設定する | 締切前にキャンセルすると残り回数が1増える | 1 |
| RS-05 | 締切後のキャンセル、当日キャンセル、無断欠席では回数を戻さない | 締切後にキャンセルしても残り回数は変わらない。無断欠席でも予約時に使った回数は戻らない | 1 |
| RS-06 | 予約を即確定にするか、管理者の承認制にするかを設定する | 承認制のときは、管理者が承認するまで「仮予約」と表示される | 1 |
| RS-07 | 管理者は、公開期間より先の日付や締切後でも予約を入れられる。繰り返し予約で毎週固定の枠を作れる | 管理者が毎週の繰り返し予約を作ると、各回が生徒の予約一覧に表示され、各月の回数から使われる。回数が足りない月は管理画面に警告が出る | 1 |
| RS-08 | 個人レッスンとグループレッスンを設定できる。グループは定員を設定する | 定員に達した枠は予約できない | 1 |

| PY-04 | 自動課金（カード、Apple Pay、Google Pay）を標準として勧める。毎月1日に課金する | 入会画面で自動課金が最初に「おすすめ」として表示される | 1 |

| PY-06 | 現金の生徒は、管理者がスマホで「入金済み」にすると回数が付く | 入金記録に日時・金額・方法「現金」・操作した人が残る | 1 |
| PY-07 | 回数の有効期限と、翌月への繰越の可否・上限を設定する | 設定に従って月初に失効・繰越が処理される | 1 |
| PY-08 | 講師都合・教室都合のキャンセルでは、使った回数を戻す | 該当の予約が取り消されると、残り回数が戻る | 1 |
| PY-09 | 月ごと・生徒ごとの入金状況一覧で、未払いの生徒を抽出できる | 一覧で未払いだけに絞り込める | 1 |
| PY-10 | 未払いの猶予期間（日数は設定値、初期値は7日）を過ぎたら予約を止める | 猶予期間を過ぎた未払いの生徒は予約できない | 1 |
| PY-11 | 決済に失敗したら、カードの更新や再認証ができるStripeの画面へのリンクをメールで送る | 失敗時にメールが送られ、リンクからカードを更新できる | 1 |

| PY-14 | 月額料金の改定時に、既存の生徒にも適用するか（適用日を指定）、新規の生徒だけにするかを選べる | 選んだ方式で、次回以降の課金額が変わる | 1 |

| PY-17 | 教材費・発表会費などの単発の請求を作り、生徒ごとに入金状況を管理する | 請求ごとに未払い・入金済みが一覧で分かる | 2 |

### 3.10 管理者のダッシュボード

| URL-03 | `hanamarumusic.com/student` と `hanamarumusic.com/staff` を開いた人も、それぞれのログイン画面へ自動で転送する（Cloudflareの転送ルール） |

パス（`/student`）ではなくサブドメインで分ける理由:

- 公開ページ（Cloudflare Pages）とログイン後の画面（VPS）は置き場所が違う。同じドメインの中でパスごとに振り分けるにはWorkersが必要になり、その分のリクエストが課金や無料枠の対象になる
- ホーム画面アプリの範囲を、生徒・講師それぞれの画面にはっきり区切れる
- ログイン情報（Cookie）が画面ごとに分かれ、混ざらない
- 講師と管理者を分けることで、管理画面だけにCloudflare Accessで強い入口制限をかけられる。管理画面のURLを講師に知られても入れない

サブドメインの名前（student、staff、manage）は変えてもよい。

## 5. 非機能要件

### 5.1 課金の上限（DoS対策）

攻撃されても請求が大きく膨らまない構成にする。定額や無料枠を基本とし、従量課金は安い場合に限り、次の条件を満たして使う。

| ID | 要件 |
| --- | --- |
| NF-01 | サーバーは転送量で課金されない定額のVPSにする |
| NF-02 | Cloudflareの無料プランでDNS、DDoS緩和、WAFを使う。Cloudflareは[DDoS緩和を従量課金なしで提供](https://www.cloudflare.com/products/ddos)している |
| NF-03 | ログイン・登録・決済開始などのURLにWAFのレート制限をかける。WAFで止めたリクエストはWorkersの課金に数えられない |
| NF-04 | 従量課金のサービスを使うときは、最悪ケースの費用を見積もって松田さんと合意し、予算アラートを設定する |
| NF-05 | 転送量で課金されるクラウド（AWS等）と、上限なしで追加配信されるLINEのスタンダードプランは使わない |
| NF-06 | 自己登録・問い合わせなどのフォームにCAPTCHA（Cloudflare Turnstile）を付け、ボットによるメール大量送信を防ぐ |

### 5.2 セキュリティ

- VPSはCloudflare Tunnel経由で公開し、受信ポートをすべて閉じる
- 通信はすべてHTTPS。パスワードはハッシュ化して保存する
- 決済画面はログインした生徒にしか出さない（盗んだカードを試す不正決済の標的にしないため）
- 権限の自動テストを必須にする: 生徒が他の生徒の予約・連絡先・入金情報を見られないこと、講師が担当外の情報を見られないこと
- OSS・OSのセキュリティ更新を月1回確認して適用する

### 5.3 可用性・性能

- 想定規模は生徒数百人まで、同時アクセス数十。2GB程度のVPSで足りる
- 業務時間帯に使えればよい（稼働率の契約は不要）。障害時は電話での予約受付で代替する
- 外形監視で停止を検知し、作成者に通知する

### 5.4 バックアップ・復旧

- データベースを毎日自動でバックアップし、VPSとは別の場所（Cloudflare R2の無料枠など）に30日分保管する
- 四半期に1回、実際に復元できるかを確かめる
- 設定とコードはGitHubにあるため、サーバーを作り直しても再構築できる

### 5.5 個人情報

- 取得する情報: 生徒名、保護者名、メール、電話番号、住所、生徒の状態、備考、レッスン記録、予約履歴、入金記録。生年月日は取らない。カード情報は持たない
- すべてを閲覧できるのは松田さんと作成者。講師は担当生徒の名前・電話・メール・講師用備考・レッスン記録だけ（SR-06）。住所は松田さんだけが見る
- 不正アクセスによる漏えいは、人数に関係なく[個人情報保護委員会への報告と本人への通知が義務](https://www.ppc.go.jp/news/kaiseihou_feature/roueitouhoukoku_gimuka/)になる。速報はおおむね3〜5日以内
- 実際の生徒を登録する前に、プライバシーポリシーを用意する。オンライン決済を始める前に、特定商取引法の表記を用意する（文面は後で決める）
- 開発・検証はダミーデータで行う

### 5.6 運用と信頼性

| ID | 要件 |
| --- | --- |
| OP-01 | `hanamarumusic.com` から送るメールに、送信元の正当性を示す設定（SPF、DKIM、DMARC）を行う。招待やパスワード再設定のメールが迷惑メールに振り分けられないようにするため |
| OP-02 | Stripeからの通知（Webhook）は、同じ通知が2回届いても回数を二重に付与しない作りにする。通知が届かなかった場合に備え、未処理の決済を定期的に照合する |
| OP-03 | 管理者の操作（入金記録、回数の手動調整、解約・休会、担当講師の変更、設定の変更）は、誰が・いつ・何をしたかを記録し、管理画面で見られるようにする |
| OP-04 | 回数の増減はすべて履歴として残し、「なぜ今この回数なのか」を生徒ごとにたどれるようにする（問い合わせ対応のため） |

## 6. 技術構成と費用

### 6.1 構成要素

| 要素 | 技術 | 置き場所 | 役割 |
| --- | --- | --- | --- |
| API（予約の中核） | TypeScript（Node.js、Hono）＋PostgreSQL | VPS（Docker） | 講師・教室・空き時間・予約・回数・Stripe連携・招待コード・通知・定期処理。業務ルールはここだけに置く |
| 画面 | TypeScript（React） | VPS（Docker、Caddyで配信） | 生徒（ホーム画面アプリ）・講師・管理者の3つの画面。APIだけを呼ぶ |
| 公開トップページ | 静的HTML | Cloudflare Pages | 教室名とログインの入口だけ |
| 公開の入口 | Cloudflare（無料プラン）: DNS、Tunnel、WAF、Turnstile | Cloudflare | 受信ポートを開けずに公開し、攻撃を手前で止める |
| 決済 | Stripe（Checkout、Billing、カスタマーポータル、Webhook） | Stripe | 決済画面、毎月1日の自動課金、カード管理 |
| メール送信 | 無料枠のある送信サービス（未選定） | 外部 | 招待、パスワード再設定、予約・課金の通知 |
| バックアップ | Cloudflare R2（無料枠） | Cloudflare | データベースの毎日のバックアップ |
| ソースコード | GitHub（非公開リポジトリ） | GitHub | コード、設定、この要件定義書 |

ドメインは作成者名義のCloudflareアカウントで取得済み。DNSやTunnelを設定する前に、松田さん名義のCloudflareアカウントへ移す（[両方のアカウントの承認で移せる](https://developers.cloudflare.com/registrar/account-options/inter-account-transfer/)）。契約はすべて松田さん名義にする。

### 6.2 月額費用（松田さんの負担）

サーバー代は月1,100〜2,000円程度の定額。ほかにドメイン代と決済手数料がかかる。

| 項目 | 月額の目安 | 備考 |
| --- | --- | --- |
| VPS（2GB程度） | 1,100〜2,000円 | さくらのVPS（年間契約で1,594円）またはConoHa VPS。XServer VPSは2GBの新規申込を停止中 |
| Cloudflare | 0円 | 無料プラン |
| ドメイン | 月数百円（年払い） | 種類で変わる |
| メール送信 | 0円 | 無料枠内 |
| 決済手数料 | 売上の数% | 手段ごとの率は契約時に公式料金で確認 |
| 保守費 | 未定 | 作成者との契約で決める |

従量課金のPaaS（Railwayなど）も比べたが、常時動かす予約システムでは定額VPSより安くならず、攻撃時に通信量の分だけ請求が増えるため採用しない。

### 7.1 フェーズ0: 検証（完了）

### 7.2 GitHubでの管理

- 非公開リポジトリを1つ作り、コード、Docker構成、Cloudflare等の設定、この要件定義書（`docs/requirements.md`）をまとめる
- リポジトリの持ち主: 作成者のアカウント（決定）。保守契約が終わるときのコードの引き渡し方法を、松田さんとの契約書に書いておく
- Claude Codeは作業ごとにブランチを作り、プルリクエストを出す。作成者がレビューしてからmainに取り込む。mainへの直接の書き込みはしない
- プルリクエストごとにGitHub Actionsで自動テストを実行する。テストが通らないものは取り込まない
- 公開するときは版番号のタグ（v0.1.0など）を付け、そのタグを本番に反映する。問題があれば1つ前のタグに戻す
- 秘密情報（APIキー、パスワード）はリポジトリに入れない。値の入っていない見本（`.env.example`）だけを置く
- リポジトリの直下にClaude Code向けの指示書（`CLAUDE.md`）を置き、7.3のルール、テストの実行方法、要件IDの参照方法を書く

**本番と検証環境**: 本番とは別に検証環境を用意する。検証環境はStripeのテストモードとダミーデータで動かし、Claude Codeの作業と受入テストはすべて検証環境で行う。本番への反映は、検証環境で確認したタグだけを使う。

### 7.3 AIのガードレール

| ルール | 理由 |
| --- | --- |
| 本番の秘密情報（Stripeの本番キー、本番DBのパスワード）をAIの作業環境に置かない。AIはテストキーとダミーデータだけを使う | 漏えいと誤操作の防止 |
| 本番DBに直接アクセスさせない。データ移行のスクリプトはAIが書き、実行は作成者が行う | 誤削除の防止 |
| 認証・権限・個人情報の実装もAIに任せるが、5.2の権限テストを必須にし、別のAIでもレビューする | 他人の情報が見える不具合の防止 |
| 決済の本番切替と、本番への反映は作成者が承認して行う | お金が動く操作は人が判断する |
| 新しい外部サービスや依存ライブラリの追加は作成者が承認する | 費用とセキュリティの管理 |
| 従量課金のサービスを有効にするときは、5.1の条件を作成者が確認する | 想定外の請求の防止 |
| 要件にない機能を勝手に足さない。迷ったら質問を残して止まる | 仕様のずれの防止 |
